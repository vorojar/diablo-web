# Sprite Pipeline 借鉴落地路线

## 目标

借鉴 LayrKits/Sprite-Pipeline 的资源生产纪律，把菠萝战纪的角色、怪物和特效素材从“手工替换后进游戏观察”升级为“离线处理、自动检查、预览验收、再接入游戏”的闭环。所有步骤必须直接服务于现有问题：动画漂移、帧配置易错、运行时抠背景、资源替换后缓存和配置不同步、特效表现不足。

## 分阶段路线

| 阶段 | 要做什么 | 为什么必要 | 解决的问题 | 直接好处 | 验收标准 |
| --- | --- | --- | --- | --- | --- |
| 1 | 建立资源合同与本地检查脚本 | 当前帧尺寸、行数、列数写在 `game.js`，PNG 改动后没有自动校验 | 图集尺寸和配置不匹配、空白或错行动画只能进游戏后发现 | 换图前先失败，避免把坏资源接入运行时 | 脚本能检查主角/怪物图集存在、PNG 尺寸、行列整除、声明帧尺寸一致 |
| 2 | 做静态 sprite 预览器 | 游戏内验证路径太长，战斗动作和 Boss 动作不容易逐帧看 | FPS、帧顺序、翻转、动作行错误难定位 | 不启动游戏流程也能快速看动作质量 | 可以选择角色/怪物、动作、方向、FPS、背景色并播放 |
| 3 | 把背景清理前移到离线管线 | 当前 `game.js` 加载图片后遍历像素抠背景，属于运行时补救 | 启动成本、边缘误伤、每次加载重复处理 | 游戏只加载已清理 PNG，运行时代码减少 | 新资源透明背景直接通过检查，运行时抠背景逻辑可删除 |
| 4 | 建立资源晋升目录 | 现在最终图、源图、实验图没有明确生产流转 | 临时素材容易混入正式资源，无法回溯来源 | 只有验收通过的 sheet 进入根目录或正式 assets | `assets-src/`、`work/`、`final/` 或等价目录职责清晰，临时产物不进版本库 |
| 5 | 生成 sprite manifest，逐步替代硬编码行号 | `HERO_SPRITE_CONFIG` 和 `MONSTER_SPRITE_CONFIG` 是事实源，但和素材生产没有连接 | 新增动作/怪物时容易改错行号、FPS 和帧数 | 资源管线输出配置，游戏消费配置，减少人工同步 | 游戏从 manifest 读取至少一类图集配置，旧硬编码相应删除 |
| 6 | 优先制作 VFX 图集 | 当前技能命中特效主要靠 Canvas 图形，视觉上不如角色贴图提升明显 | 火球、闪电、多重箭反馈不够有辨识度 | 最小资源量带来最大战斗爽感提升 | `vfx_sheet.png` 有命中/爆炸/闪电节点动画，并有预览和配置 |
| 7 | 强化 Boss 攻击预警帧 | Boss 技能已有机制，但读招主要靠粒子和文字反馈 | 难度公平性不足，玩家不知道何时该躲 | Boss 更像有招式的敌人，而不是数值怪 | 每个关键 Boss 至少一个可读攻击前摇动画或预警特效 |
| 8 | 最后重做普通怪和主角动作 | 全量重做成本最高，且前面管线未稳定前容易返工 | 普通怪动作质量不均、主角动作有限 | 在稳定管线下批量升级，不重复返工 | 新动作通过脚本、预览器和真实战斗冒烟验证 |

## 执行原则

- 先做能防错的工具，再做大量新素材。
- 先处理玩家高频看到的战斗反馈，再处理低频美术补全。
- 正式 VFX、角色和怪物图集优先使用 AI 位图生成或人工绘制的美术资产；程序生成图只用于占位、测试管线和快速验证。
- 不把 Python、FFmpeg 或图片处理逻辑放进游戏运行时。
- 不新增第二套配置事实源；在 manifest 未接管前，检查脚本以 `game.js` 现有配置为准。
- 每次更新 JS 或 CSS 才更新 `index.html` 版本号；只改文档和工具不改缓存版本。

## 当前第一步

先落地“资源合同与本地检查脚本”。它成本低、风险小，能立刻保护现有 `hero_sprites.png` 和 `monster_sprites.png`，也是后续预览器、离线清理和 manifest 的基础。

## 第一条完整闭环：火球命中爆炸 VFX

选择火球命中爆炸作为第一条完整闭环，因为它是高频战斗反馈，接入面小，不改角色/怪物状态机，也不改变技能伤害判定。它用于验证整条资源链路：AI 位图生成或人工绘制、manifest 声明、脚本检查、静态预览、游戏内真实命中播放。程序生成图只保留为管线占位方案，不作为最终视觉标准。

| 环节 | 落地文件 | 验收方式 |
| --- | --- | --- |
| 图集生成 | AI 位图源图、`tools/promote-ai-vfx-sheet.ps1`、`vfx_sheet.png` | 生成 `1024 x 128` 透明横向图集 |
| 配置事实源 | `vfx-manifest.js` | 声明 `fireballImpact` 的帧宽、帧高、帧数、FPS、pivot 和渲染尺寸 |
| 资源检查 | `tools/validate-sprite-assets.ps1` | 同时检查主角、怪物和火球 VFX 图集合同 |
| 静态预览 | `sprite-vfx-viewer.html` | 直接通过浏览器播放火球命中爆炸 |
| 游戏接入 | `game.js`、`index.html` | 火球命中敌人、墙体或可破坏物时播放序列帧 VFX |

## 第二条完整闭环：闪电与多重射击命中 VFX

闪电命中和多重射击命中作为第二批一起做，因为它们复用火球命中的资源链路和同一个 `emitSkillImpactBurst()` 接入点。图集从单行升级为多行：第 1 行 `fireballImpact`，第 2 行 `thunderImpact`，第 3 行 `multishotImpact`。检查脚本和预览器必须按 manifest 枚举所有效果，不能只校验火球。

## 第三条完整闭环：通用反馈 VFX

升级、暗金/套装掉落、回城传送门开启和药水使用作为第三批一起做，因为它们都是高频、瞬时、发光型反馈，不改变战斗判定和角色状态机。图集继续使用纯黑底 additive 源图，第 4 行 `levelUpBurst`，第 5 行 `rareDropBurst`，第 6 行 `portalOpen`，第 7 行 `potionUse`。接入点必须放在业务动作已经成功发生之后：升级函数、稀有掉落创建、回城施法启动、药水实际消耗。

## 第四条完整闭环：Boss 技能读招 VFX

Boss 施法蓄力、圆形危险区、扇形危险区和直线危险区作为第四批做，因为它们解决的是“技能即时结算、玩家看不懂为何受伤”的公平性问题。Boss 技能进入 `pendingSkill` 后先播放 0.45 秒预警，再按原有伤害函数结算；方向型技能锁定预警时的角度，避免提示方向和最终判定不一致。

## 第五条完整闭环：状态触发 VFX

状态反馈先检查已有表现再补缺口。冰冻/减速已有角色和怪物冰蓝 tint、血球 chilled 状态；护盾已有常驻椭圆光环和血球叠层，所以不重复添加常驻 VFX。本批只补中毒首次进入、闪电过载首次进入、护盾施放和护盾吸收这些“发生瞬间”的场景反馈，避免 DOT 每跳或护盾常驻期间持续刷特效。

## 美术资产纪律

火球命中爆炸 VFX 已从程序占位图替换为 AI 生成位图资产。后续新增正式 VFX 时，默认流程是：先生成或绘制高质量位图源图，再用 `tools/promote-ai-vfx-sheet.ps1` 晋升为游戏图集，最后通过 `tools/validate-sprite-assets.ps1` 和预览器验收。不要把程序生成图作为正式美术提交。

## 本次踩坑与硬规则

| 坑 | 根因 | 以后怎么一次到位 |
| --- | --- | --- |
| 生成了 AI 图但没替换进项目 | 把“生成图片”和“晋升为正式资源”当成同一步，缺少替换验收 | AI 生成后必须执行晋升脚本，确认 `vfx_sheet.png` 的文件时间、大小和预览器显示都已变化 |
| 用程序图当正式图 | 为了先跑通管线，临时图没有明确标记为占位 | 正式提交前必须替换为 AI 位图或人工绘制资产，程序图只允许用于红绿验证 |
| AI 图看起来透明但实际有棋盘格底 | 图片预览的透明格被模型画进了像素，不是真 alpha | 晋升脚本必须先去背景，并在黑色/深色预览器中检查没有浅色底纹 |
| 简单等宽切帧会切出残片 | AI 生成的 8 帧间距不严格等宽，火星会跨越理论边界 | 晋升脚本必须按内容分段识别 8 个帧块，再缩放到固定帧格 |
| PowerShell 参数名踩 `$input` | `Input` 和 PowerShell 自动变量冲突，导致路径传参异常 | 脚本参数避免使用 `Input`，使用 `SourcePath`、`OutputPath` 这类明确名称 |
| 参数默认值依赖 `$PSScriptRoot` 失败 | PowerShell 在参数默认值阶段对脚本路径处理不稳定 | 路径默认值放到脚本主体里初始化，不放在 `param` 默认表达式里 |
| 预览通过不等于游戏接入通过 | 静态 HTML 只验证图集播放，不验证游戏命中路径 | 必须同时做脚本检查、预览器截图、HTTP 加载和游戏运行时创建 VFX 的冒烟 |
| 提交时容易混入历史脏改 | 工作区已有 `game.js/index.html/style.css` 未提交改动 | 提交前用 `git diff --cached --stat` 和 `git diff --cached --check` 核对原子范围，只提交本次闭环文件 |
| 预览器里好看但真实场景过大、漂浮 | 只按图集视觉调参，没按角色比例和地牢背景校准 | VFX 首次接入默认按角色 `renderSize` 的 90%-110% 估算，命中爆炸 pivot 放在底部 75%-82% 位置，并用真实场景截图验证 |
| 烟尘在绿色地牢里发白 | AI 烟尘高亮偏灰白，和暗色地牢不融合 | 晋升后半段烟尘帧要压暗、偏暖、降低 alpha，避免白边和抠图感 |
| 棋盘格源图会造成永久白边 | 模型把“透明预览格”画进像素，柔边已经和浅底混色 | 禁止接受棋盘格源图；优先生成真实 alpha PNG，做不到时改用纯黑底 additive 图，游戏内用 `lighter` 混合 |
| 灰色分隔线也会被模型画进黑底源图 | AI 遵守了黑底，但仍把网格线当成图像内容 | 黑底 additive 晋升脚本要清除低亮度低饱和背景线；方向/长条 VFX 必须用 `-UseSourceGrid` 按格切帧 |

后续做闪电、箭矢、Boss 预警或角色动作时，验收顺序固定为：AI/人工源图 -> 晋升脚本 -> 资源合同检查 -> 预览器截图 -> 游戏真实入口冒烟 -> 原子提交。

## 后续可合批原则

发光型、瞬时型、无复杂判定的 VFX 可以合批做，例如命中爆点、传送光、掉落闪光、升级闪光。这类资源优先走纯黑底 additive 源图，游戏内用 `lighter` 混合。会改变战斗读招、持续区域、状态覆盖、角色动作或怪物状态机的内容不要混在同一批，必须单独验收。
